Server Actions are framework-generated POST entry points, not versioned REST
endpoints. Treat every action as an untrusted boundary and enforce
authorization/validation inside the action. Exact request/response shapes are in
the TypeScript signatures. Several implementation helpers under nested files are
not listed unless re-exported by a top-level action module.

## Authorization Notes

- Admin modules accept a token argument in many operations and check
  `isAuthorizedUser`; verify each implementation, not just the UI route.
- Payment methods distinguish signed-in user operations and admin submission
  review.
- Game score actions validate one-time session, owner/game, time, limits and
  score server-side.
- PPF actions resolve either an authenticated user or sanitized guest ID.
- Tax AI requires admin or active Tax Pro subscription.
- `getShiprocketAuth` and `shiprocketFetch` are async exports from a
  `'use server'` module without explicit auth in the wrapper. Source search
  found no direct client call sites for those two helpers, and Next build docs
  state unused action references may be removed; exact generated action
  reachability is NOT VERIFIED. If callable, `getShiprocketAuth` returns
  token/profile data (including sensitive DB fields) and `shiprocketFetch`
  accepts an arbitrary endpoint/options. Treat as a HIGH-priority security
  review item until the built action manifest and deployment behavior are
  confirmed.

## Local Build Reachability Check

Source search found no direct client call sites for `getShiprocketAuth` or
`shiprocketFetch`, and the current `.next/static` scan found no helper-name
references. The local server reference manifest did not map action entries to
the source module by string. This lowers but does not eliminate exposure risk:
production build/deployment artifacts may differ, and framework action IDs are
not human-readable. Treat these wrappers as internal-only in source and confirm
their registration in the production build before considering the review closed.

No generated OpenAPI/Zod contract covers these functions as a set. This document
inventories names, not every field/error/side effect. Use each action’s
implementation and tests for exact behavior; add validation/auth tests when
contracts change.
